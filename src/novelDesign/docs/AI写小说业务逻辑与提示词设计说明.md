# AI写小说业务逻辑与提示词设计说明

**此文件AI不允许修改**

## 1. 整体概述
本工具主要是一个三栏布局的AI辅助小说创作应用（忽略header），核心交互模式为：用户在右侧AI对话区发送指令，AI通过一系列工具调用和内容生成，操作左侧章节导航与中间小说正文编辑器。所有AI回复需通过 `ant-design-x` 的 `ThoughtChain` 组件展示，模拟“思考 → 执行 → 生成”的可视化流程。

## 2. 界面与数据交互约定
- **左侧：章节导航**  
  包含固定首项「故事大纲」，其余为可排序、可操作的章节列表（1、集标题 ...）。  
  高亮项表示当前激活章节，中间编辑器同步展示该章节内容。
- **中间：小说正文编写区**  
  采用 Milkdown 编辑器，展示当前激活章节的 Markdown 内容。  
  AI 生成的 `novel-body-json` 代码块会被前端解析后以流式方式预览写入，完成后正式写入编辑器并自动保存到本地数据库。
- **右侧：AI对话区**  
  使用 `ThoughtChain` 组件展示 AI 思考链，包含工具调用的状态、小说生成的 loading 动画、最终结果及下一步操作建议。
- **关键数据对象**  
  - 故事大纲：一个独立的 Markdown 文档，通过 `novel_story_outline_get/update` 读写。  
  - 章节内容：每个章节保存为 `{ n, title, content_markdown }`，通过相关工具操作。

## 3. 核心操作流程：以 “帮我新增一集” 为例

### 3.1 整体流程图（AI需严格执行）
```
用户输入 → AI判断意图为“新增一集”
    ↓
步骤1：检查故事大纲是否存在（调用 novel_story_outline_get）
    ├─ 不存在或无权限 → 回复提示：“没有找到故事大纲，请输入创作要求生成故事大纲 或 退出小说编辑界面并使用故事抽卡功能”
    └─ 存在 → 获取大纲正文，进入步骤2
    ↓
步骤2：获取最后一集信息（调用 novel_episodes_list 获取列表，或 novel_episode_content_get 读取最后一集正文）
    ├─ 没有最后一集（章节列表空） → 调用 novel_episode_create 创建第1集（标题可取自大纲第一段或默认“第1集”），同时 novel_episode_active 打开该集
    └─ 有最后一集 → 读取其内容，AI判断是否为有效小说正文（非大纲、非空、非纯笔记等），且故事是否已完结/该章是否完整
         ├─ 不是小说内容或不完整 → 不新增，视为“重写/续写当前最后一集”。AI回复提示：“检测到最后一集[标题]内容可能不是正文或不完整，是否清空并重写？”等待用户确认。
         └─ 是完整小说正文 → 调用 novel_episode_create 新增一集（编号递增，标题结合大纲智能生成），再 novel_episode_active 打开新集
    ↓
步骤3：AI在对话区输出思考链（ThoughtChain）
  - 展示判断与工具调用结果（如：“最新一集是第5集，剧情发展到顾清寒买下空地...接下来按大纲应该是第6集「辣子的逆袭」...”）
  - 进入“撰写正文”阶段，显示 loading 状态
  - 以流式方式输出包含 novel-body-json 代码块的内容，前端解析后同步更新到中间编辑器（预览区）
  - 输出完成，显示“✅ 第6集「辣子的逆袭」的正文已经撰写完毕”，前端将预览内容正式写入 Milkdown 并触发保存
    ↓
步骤4：连续创作判断
  - 若用户要求连续创作（如“帮我生成接下来三集”），则在上一集完成后自动重复步骤2-3（循环）
    ↓
步骤5：输出下一步操作建议
  - 以按钮或建议条形式展示：新增一集、续写内容、重写本集、润色润稿等（列表见第4节）
```

### 3.2 AI判断“最后一集是否为完整小说内容”的逻辑
- 完整小说章节应包含：场景描写、对话、动作、情节推进，有明显的起承转合，末尾通常有悬念或过渡，而非“大纲：第一章 xxx”。  
- 不完整的标志：内容过短、以大纲条目为主、结尾明显中断（如句子未结束）、含有“待续”“TBD”等标记。  
- 如果模糊，保守处理：询问用户。

### 3.3 流式输出与编辑器联动细节
- AI 输出 `novel-body-json` 代码块时，前端监听流式数据，解析出 JSON 后提取 `content_markdown`，实时渲染到中间编辑器的预览层（区别于正式文档）。
- 流式结束（代码块闭合），前端将预览内容转移至 Milkdown 正式文档，并调用工具 `novel_episode_content_replace` 或直接替换当前活动的章节数据（若为新建章节则创建后再保存）。
- **注意** `novel_write_payload` 中的 `mode` 字段：新建章节时用 `"append"`，重写某集时前端可能使用 `"replace"`。

## 4. 工具函数规范与使用约束

| 工具名称 | 说明 | 调用限制 |
|---------|------|---------|
| `novel_story_outline_get` | 获取故事大纲全文 | 任何涉及大纲的操作必须先调用 |
| `novel_story_outline_update` | 更新大纲内容 | 仅当用户明确要改大纲时使用 |
| `novel_episode_create` | 创建新集，参数：`n`(集号)、`title`、`content_markdown`(可为空) | 集号必须为正整数且连续，通常为最大集号+1 |
| `novel_episode_active` | 切换编辑器到指定集 | 参数 `n` |
| `novel_episode_content_get` | 读取某集正文 | 参数 `n`，读取后用于判断、续写、重写等 |
| `novel_episode_content_replace` | 精确替换指定文本 | 替换整个章节内容时，将整个内容作为旧文本替换为新文本 |
| `novel_episode_content_delete` | 删除指定文本 | 用于局部删除 |
| `novel_episode_rename` | 重命名集 | 禁止重命名大纲（即集号为0的虚构项） |
| `novel_episode_delete` | 删除单集 | 删除后需调整编号 |
| `novel_episodes_delete_from_to` | 删除连续多集 | `to`为空则删除`from`及之后所有 |
| `novel_episodes_list` | 列出所有集（返回编号和标题列表） | 获取最后一集信息时优先使用 |
| `novel_episode_exists` | 检查某集是否存在 | |
| `novel_rename` | 修改小说整体标题 | 不常用 |
| `novel_episodes_reorder` | 调整集顺序 | 支持拖拽后批量更新 |
| `novel_episode_split` | 拆分一集为两集 | 需指定分割位置 |
| `novel_episodes_merge` | 合并多集 | |

**核心约束**：
- 工具调用需遵循真实数据库情况，不可凭空创建已存在的集。
- 所有工具调用结果必须在思考链中简要展示，但不必暴露原始 JSON。
- 若工具调用失败（如大纲不存在），必须在思考链中展示友好错误提示，并停止流程。

## 5. 小说内容输出规范（`novel-body-json`）

AI 创作的小说正文必须用以下格式包裹，且**不能包含标题行、分隔线、完结标记、总结语**：

```
```novel-body-json
{"novel_write_payload":{"n":6,"mode":"append","title":"辣子的逆袭","content_markdown":"<纯正文 Markdown>"}}
```
```

- `n`：集号，必须与当前操作的目标集一致。
- `mode`：
  - `"append"` 用于新建集或在末尾追加内容。
  - `"replace"` 用于完整替换某一集的内容（如重写本集）。
- `title`：章节标题（不含“第X集”编号，编号由前端显示），建议从大纲提炼。
- `content_markdown`：仅包含正文，不得出现 `# 标题`、`---`、`（完）` 或任何总结性语句。允许分段、对话格式。

**示例**：
```
```novel-body-json
{"novel_write_payload":{"n":6,"mode":"append","title":"辣子的逆袭","content_markdown":"夜色如墨，姜辞刚锁好店门，身后便响起杂乱的脚步声。\n\n“妹子，保护费该交了吧？”刀哥叼着烟，身后跟着五六个混混。\n\n姜辞转身，嘴角勾起一抹笑：“保护费没有，新研制的‘地狱鸡翅’倒可以请你们尝尝。”\n\n……"}}
```
```

## 6. 提示词设计（角色分配）

### 6.1 System Prompt（系统提示词）
放置位置：语言模型系统级指令，定义AI角色与基础行为。

内容要点：
```
你是一个专业的小说创作AI助手，工作于一个三栏式写小说界面中。
你必须严格遵循以下规则：
1. 所有操作均基于工具调用，不可自行假设数据存在。
2. 执行“新增一集”“续写”等操作前，必须先检查故事大纲是否存在，然后检查最后一集状态。
3. 所有回复必须使用 ThoughtChain 可展示的结构：思考过程 → 工具调用（如有）→ 正文输出。
4. 正文输出必须使用 ```novel-body-json 代码块，遵循字段定义，且 content_markdown 中不能包含标题、分隔线、完结标记或总结语。
5. 完成正文输出后，必须提供下一步操作建议（以按钮形式呈现的建议列表）。
6. 若遇到需要用户确认的情况（如清空重写），必须停下并明确询问。
7. 保持故事一致，根据故事大纲和已有章节内容延续剧情，人物性格、设定不得偏离。
8. 工具调用结果若需展示，用自然语言简要描述，不要输出原始JSON。
```

### 6.2 User Prompt 构建规则
用户输入分为两类：意图指令和内容补充。前端可根据上下文组装 user 消息。

**示例1：简单指令**
```
User: 帮我新增一集
```
此时系统应直接进入前述流程。

**示例2：带要求的指令**
```
User: 新增一集，要重点描写姜辞的心理活动。
```
AI 在生成正文时需融入这个要求。

**示例3：组合指令（连续创作）**
```
User: 根据大纲连续生成接下来的三集。
```
AI 需要循环执行新增流程，每完成一集后判断是否继续，直到生成三集或用户终止。

**示例4：对已有内容操作**
```
User: 重写第3集，增强冲突。
```
AI 调用 `novel_episode_content_get(n=3)`，获取原内容，结合要求生成新正文，并通过 `novel-body-json` 以 `mode:"replace"` 输出，同时调用 `novel_episode_content_replace`（或由前端处理替换）。

### 6.3 Assistant 回复示例（思维链风格）
当用户说“新增一集”时，AI 的回复应模拟为：

```
好的，我先检查一下当前小说的状态。
（调用 novel_story_outline_get） … 已获取大纲。
（调用 novel_episodes_list） … 找到5个现有章节。

最新一集是第5集「意外的援军」，结尾处顾清寒与姜辞刚达成合作。按大纲下一阶段应为“辣子的逆袭——地头蛇刀哥找茬，姜辞用地狱鸡翅绝地反击”。这将是第6集，我来为您撰写。

正在撰写第6集「辣子的逆袭」的正文…… [streaming]

```novel-body-json
{"novel_write_payload":{"n":6,"mode":"append","title":"辣子的逆袭","content_markdown":"（流式正文）"}}
```

✅ 第6集「辣子的逆袭」正文已撰写完毕，已保存并打开。

接下来您可以：
- 新增一集
- 续写当前内容
- 重写本集
- 润色润稿
- 扩写细写
...
```

## 7. 其他常用操作的流程要点

### 7.1 续写内容
- 用户可能未指定集号，默认对当前激活集操作。
- 调用 `novel_episode_content_get` 获取当前集全文，在文末追加新内容，使用 `mode:"append"` 输出，前端追加到编辑器末尾。
- 思考链中提示“续写第X集...”。

### 7.2 重写本集
- 获取当前集内容，AI 根据要求或默认提升质量进行重写。
- 输出 `mode:"replace"` 的 `novel-body-json`，前端替换整个编辑器内容。

### 7.3 润色/扩写/精简/调整文风等
- 此类操作不改变集数，只修改当前集内容。
- 流程类似重写，但 AI 需要在思考链中说明做了哪些改进。
- 如果用户选定部分文本进行操作，使用 `novel_episode_content_replace` 精确替换，此时 AI 可能不输出 `novel-body-json`，而是以自然语言描述并调用工具。

### 7.4 拆集与合集
- 拆集：用户指定拆分的集号和拆分位置，AI 调用 `novel_episode_split`，并可能调整后续集编号。
- 合集：调用 `novel_episodes_merge`，可能需要 AI 生成过渡内容，可先用 `novel_episode_content_get` 获取两集内容，AI 补写衔接段落，再通过工具执行合并。

## 8. 连续创作与循环控制

当用户指令为“生成接下来的N集”或类似连续创作要求时，AI 应执行循环：
1. 判断是否有下一集大纲可循（可从大纲中提取后续章节标题/概要）。
2. 若大纲足够，按顺序生成每一集。每完成一集，前端会触发保存并可能再次询问（实际开发中由前端循环调用AI，或AI在一次对话中多轮输出多段 `novel-body-json`）。这里建议：**AI 在一次回复中最多输出一集正文，避免超过token限制**。多集生成可通过前端在工作流中连续发送“请生成下一集”来实现，AI 不需要特殊处理。但 AI 可以在完成一集后主动提示：“第X集已完成，需要我继续生成下一集吗？”然后再由用户确认或前端自动确认。

## 9. 下一步操作建议

每次完成正文操作和总结后，AI 须在回复末尾附加操作建议栏，比如：
- 继续新增1集
- 重写这集，我不满意

前端将这些建议渲染为可点击的 Suggestion 按钮（Ant Design X 的 Suggestion 组件），点击后自动发送对应指令。

## 10. 错误处理与边界情况

| 场景 | AI行为 |
|------|--------|
| 无大纲且要求生成章节 | 回复：“请先创建故事大纲。您可以在此输入创作要求，我帮您生成。”  不调用任何章节工具。 |
| 大纲存在但内容为空 | 先提示：“大纲内容为空，建议先完善大纲再生成章节。” 并询问是否先完善大纲。 |
| 删除当前激活集 | 调用删除工具后，自动激活相邻集（优先下一集，若无则上一集），并提示用户。 |
| 尝试重命名大纲 | 禁止执行，并提示“大纲名称不可更改”。 |
| 工具调用返回错误 | 展示友好信息，如“读取章节失败，请刷新后重试”，并停止流程。 |
| 用户要求清空某集 | 使用 `novel_episode_content_replace` 将全文替换为空字符串，并提示。 |

## 11. 前端与AI的协作约定（补充）

- 前端通过 AI 发送用户消息时，可附带当前上下文信息（如当前激活集号、最近几集摘要）到 Assistant 消息的 `context` 字段，但不要放入 user 消息正文，以保持对话整洁。
- AI 输出的 `novel-body-json` 仅作为内容载体，前端需额外解析并决定是否调用对应的工具进行持久化。建议：**AI 不要直接调用 `novel_episode_content_replace` 来写入全文**，而是输出代码块，由前端负责最终写入和保存，这样可以完美实现流式预览。AI 调用的工具仅限于信息查询和维护性操作（创建章节、跳转、删除等），内容写入工具由前端根据 `novel-body-json` 自动调用。
- 流式传输期间，编辑器应处于“预览模式”，禁止用户手动编辑，直到写入完成。
