# 小说编辑页代码审视意见

> 审视范围：`src/novelDesign/` 下与「小说编写工作台」直接相关的文件
> 核心痛点：一个功能被多次迭代修补，架构边界模糊，多处逻辑互相踩踏

---

## 总览

| 文件 | 行数 | 核心职责 | 主要问题 |
|------|------|---------|---------|
| `ScreenwriterNovelDetailPage.tsx` | ~1000 | 页面编排、AI 响应流处理、JSON 解析、短暂态管理 | **过载**：5+ 个职责混在一个文件 |
| `novelEditorFunctionCalls.ts` | ~783 | 13 个 AI 工具定义 | 组织尚可，但类型松散 |
| `novelWorkspaceStorage.ts` | ~448 | 数据层：CRUD + 持久化 | 基本健康，但 saveAndReturn 模式影响性能 |
| `NovelCrepeEditor.tsx` | ~155 | Milkdown 编辑器封装 | 多个 useEffect 互相竞争 |
| `novelWriteIntent.ts` | ~156 | 用户意图分析 | 尚可，但正则维护成本高 |

| `buildNovelEditorToolCommands.ts` | ~138 | A2UI 命令构建 | 可接受 |

## 一、ScreenwriterNovelDetailPage.tsx — 单一文件过载（最高优先级）

### 1.1 该文件至少承载 5 个独立职责

| 职责 | 代码区域 | 行数估算 |
|------|---------|---------|
| 页面布局与 Splitter 三栏渲染 | JSX + 布局逻辑 | ~200 |
| AI 流式写入处理（onAssistStream） | 单个 useCallback | ~250 |
| JSON / novel-body-json 解析（extractNovelWritePayload） | 模块级函数 | ~100 |
| 侧栏气泡渲染（sidePanelAssistantContentRender） | 内联 render prop | ~80 |
| Sender 选区防抖 + ContextTag 同步 | 分散的 useEffect/useCallback | ~80 |

**建议**：
1. 将 AI 流式响应处理（`onAssistStream` + 所有 AI 相关 ref）抽成自定义 Hook，如 `useNovelAiStream`
2. 将 `extractNovelWritePayload` 移到独立的 parser 模块（现在它和页面耦合在同一文件中）
3. 将 `sidePanelAssistantContentRender` 抽成独立组件
4. 将 Splitter 三栏布局的三种模式（nav+ai / nav-only / ai-only / none）抽成布局组件

### 1.2 onAssistStream 回调 — 最危险的单点故障

`onAssistStream` 是一个约 250 行的 `useCallback`，同时处理：

- 流开始/结束的短暂态管理
- `aiPendingRef` 的读写
- 工具调用追踪（`turnTouchedWriteToolRef`）
- JSON 流式解析 + 严格解析双路径
- `workspaceRef` / `setWorkspace` 双重写入
- `AUTO_JSON_RETRY` 逻辑（现已禁用但代码残留）

**具体风险**：
- `return`/`early return` 超过 10 处，路径极其复杂
- `workspaceRef.current` 和 `setWorkspace` 的同步依赖 React 效应链，上一轮修复中通过在 `setSnapshot` 里同步写入 ref 部分缓解，但未彻底解决

**建议**：
1. 将 `ended` 处理块提取为纯函数，输入 payload + snapshot，输出新的 snapshot（可测试）
2. 将「开始写入」「流式预览」「结束保存」三个阶段拆成独立函数
3. 状态机化：`idle → writing_stream → resolving → saving → idle`，用 `useReducer` 或 `useState` 的 enum 表达

## 二、双写入路径的竞态问题（高二优先级）

### 2.1 两条路径，两种解析

当前 AI 写正文有两条完全独立的路径：

**路径 A — AI 工具调用**：`novel_write_body_episode` / `novel_write_episode`
- 走 `novelEditorFunctionCalls.ts` → `applyMutation` → `setSnapshot`
- 工具返回后 AI 还会在对话区输出确认文字

**路径 B — 流式 novel-body-json**：AI 在对话输出中包含 ````novel-body-json` 代码块
- 走 `onAssistStream` → `extractNovelWritePayload` → 流式遮罩 → ended 保存
- 支持流式预览（撰写中遮罩层）

两条路径在 `onAssistStream` 里**互相取消**：

```typescript
// 路径 B 检测到路径 A 的工具被调用 → 清空 aiPendingRef
if (hasWriteToolsInTurn && aiPendingRef.current) {
  aiPendingRef.current = null;  // 取消流式写入
}
```

### 2.2 路径 B 的数据一致性问题

路径 B 在 `ended` 保存时，需要做四个相互依赖的判断：

1. **解析集序号**：`parsed.payload.n` → `parsed.streamTargetN` → `hasCreateEpisodeToolInTurn` 回退
2. **解析正文**：`parsed.payload.content_markdown` → `parsed.streamContentMarkdown`
3. **确定写入模式**：`parsed.payload.mode` → `pend.mode` → 空内容时强制 append
4. **写入**：`updateEpisodeMarkdown` + `bumpRemount`

这四步之间的回退链极其复杂，任何一步出错的后果都是「正文写入错误的目标集」或「编辑器显示空白」。

**建议**：
1. 考虑统一入口：让 AI 总是走 tool call 写入，不再依赖 `novel-body-json` 流式解析（或者反过来，让 tool call 也走同一套解析）
2. 如果保留双路径，至少让正文提取（流式/严格）收敛到同一纯函数

## 三、extractNovelWritePayload — 解析逻辑脆弱（高优先级）

### 3.1 双模式提取

同一函数内实现两种提取模式：

- **严格模式**：`NOVEL_BODY_JSON_FENCE_RE` → `JSON.parse` → 需要完美 JSON
- **宽松模式**：`extractStreamContentMarkdown` — 直接在原始文本中搜索 `"content_markdown"` 后面的值

宽松模式用手工遍历字符的方式处理 JSON 字符串中的转义，而不是用 `JSON.parse`。如果 AI 输出的 `content_markdown` 包含换行、引号、反斜杠，**即使 AI 的 output 在 LLM 维度是正确的，宽松解析也可能产生不同的结果**。

### 3.2 宽松解析 vs 严格解析的差异

```typescript
// 宽松解析 → 拿到的是 "content_markdown":"..." 的中间原始文本
const streamingBody = parsed.streamContentMarkdown;

// 严格解析 → 拿到的是 JSON.parse 之后的 content_markdown
const jsonContent = parsed.payload?.content_markdown?.trim() ?? '';
```

**问题**：流式遮罩层（撰写中）用宽松解析 → 看起来正常。保存时（ended）用严格解析 → 失败→回退到宽松解析。两个阶段显示的内容可能不同。

**建议**：
1. 统一只用严格 `JSON.parse`（只在 fence 里提取 JSON），彻底废弃宽松模式
2. 如果 AI 输出 JSON 不标准，改进 prompt 模版来约束 AI，而非在代码层做「模糊匹配」

## 四、workspaceRef 同步模式脆弱（高优先级）

### 4.1 双 source of truth

```typescript
const [workspace, setWorkspace] = useState<NovelWorkspaceSnapshot | null>(null);
const workspaceRef = useRef<NovelWorkspaceSnapshot | null>(null);
useEffect(() => {
  workspaceRef.current = workspace;
}, [workspace]);
```

`workspace` 是 React 渲染依据，`workspaceRef` 是回调中的即时读取依据。借助 `useEffect` 同步意味着：

- 同一个 React 渲染周期内，`setWorkspace(newSnap)` 后，`workspaceRef.current` **仍然是旧值**
- 工具调用 `setSnapshot` 时我们同步写 ref，但 `useEffect` 在下一帧又会覆盖它（除非值相同）

虽然上一轮修复中在 `setSnapshot` wrapper 里同步写了 ref，但这个两源模式仍然非常危险。

### 4.2 其他 ref 的同步问题

类似 `selectionPlainRef` / `selectionPlainForSenderRef` / `aiPendingRef` / `prevRequestingRef` / `autoJsonRetrySignatureRef` 等等，大量使用 ref 做「即时状态」导致代码心智负担极高。至少 8 个 ref 用于跟踪异步状态。

**建议**：
1. 考虑用 `useReducer` + 状态机替换 ref 集群，让所有状态变更可追踪
2. 如果保留 ref 模式，需要建立严格的「写 ref → setState」原子操作约束，避免在 ref 写入后、setState 生效前被其他代码读取

## 五、NovelCrepeEditor 的 useEffect 竞争（中优先级）

### 5.1 三个 effect 互相踩踏

编辑器组件在 `mount` 后有三个 `useEffect`：

1. **readOnly effect**：`view.setProps({ editable })`
2. **markdown update effect**：检测 `initialMarkdown` 变化 → 用 `parser` 重建 doc → `view.dispatch`
3. **useImperativeHandle**：`focusEditor`

问题：
- readOnly 变化时可能正处于 markdown update 的 dispatch 过程中，会产生「编辑区闪烁」
- markdown update 检测 `trimmed === lastSetMdRef.current?.trim()`，但 `lastSetMdRef` 初始值就是 `initialMarkdown`，首次挂载时不会更新

### 5.2 remountKey 设计

通过 `MilkdownProvider key={remountKey}` 彻底卸载重建编辑器，是确保 AI 写入的内容正确渲染的最后保险。但同时意味着：

- 每次外部写入都会导致编辑器**完全销毁重建**（丢失 undo stack、光标位置、滚动位置）
- `remountVersionByEpisode` 只要 bump 就会重建，即使内容没有实际改变

**建议**：
1. 用 `replaceWith` 替换 doc（已有实现）替代 remount，只在 `providerKey`（切换集）时重建
2. 为 `updateEpisodeMarkdown` 增加「内容未变化时不 bump remount」的短路逻辑

## 七、其他细节问题（低优先级）

### 7.1 已禁用的代码残留

- `AUTO_JSON_RETRY_ENABLED = false` 但相关分支代码仍完整保留（约 30 行），增加阅读负担
- `looksLikeConfirmationOnly` 函数定义在 `novelEditorFunctionCalls.ts` 中，仅被 tool handler 使用，但位于文件作用域顶层

### 7.2 正则维护成本

- `novelWriteIntent.ts` 中大量正则用于判断用户意图，`WRITE_INTENT_RE` 覆盖 20+ 个关键词，这种模式会导致用户自然语言变体遗漏
- 建议考虑用语义相似度（或 AI 自身判断）替代关键词匹配

### 7.3 性能关注点

- `saveAndReturn` 模式：每次 `setActiveEpisode`、`upsertEpisode`、`updateEpisodeMarkdown` 都立即写 `localStorage`。用户快速切换集或 AI 流式写入时，可能产生大量不必要的序列化
- `formatNovelContextTags` 在每次 AI 发送消息时都重新截取大纲和当前正文（最多 32KB 字符串操作），内容未变化时浪费计算

### 7.4 测试覆盖

整个 novelDesign 目录下仅有 1 个测试文件（`screenwriterStoryPayload.streaming.test.ts`），核心逻辑如 `extractNovelWritePayload`、`onAssistStream` 的 `ended` 块处理完全无测试覆盖。
